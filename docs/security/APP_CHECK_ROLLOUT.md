# Firebase App Check rollout

App Check client initialization is shipped in monitor mode. Enforcement is
intentionally disabled until attestation metrics prove that legitimate clients
are covered. No debug token belongs in source control, build arguments,
documentation, CI logs, or a distributed APK.

## Client behavior

| Build | Android provider | Distribution rule |
| --- | --- | --- |
| Production release | Play Integrity | Play/internal testing tracks, then production |
| Production debug | Debug | Local development only; never distribute |
| Staging debug or release | Debug | Approved testers only |
| Web | Not activated yet | Do not enforce until a web provider/site key is configured |

The SDK is activated after `Firebase.initializeApp()` and before Firebase
services are used. Debug tokens are generated by the native SDK at runtime and
must be registered manually in the matching Firebase project. They are never
embedded by this repository.

## Resources to protect

All callable Functions should eventually require App Check. Prioritize the
expensive or security-sensitive endpoints:

1. `askTutor`, `generateQuiz`, `generateSummary`;
2. `submitMobileMoneyPayment`, `reviewMobileMoneyPayment`,
   `listMobileMoneyPayments`, `getMobileMoneyOverview`;
3. `reviewStaffAccount`, `submitStaffRegistration`,
   `requestAccountDeletion`;
4. the quiz, progress and Flow callables.

After callable coverage is stable, enable enforcement for Cloud Firestore and
Cloud Storage. Authentication App Check remains a later, separately monitored
step because its enforcement support and client-impact profile differ.

No callable currently sets `enforceAppCheck: true`, and handlers do not reject
requests based on `request.app`. The callable runtime will still verify and log
App Check tokens when present, which supplies monitor-mode coverage data.

## Manual Firebase and Google Play actions

Perform these actions separately in both Firebase projects. Do staging first.

### Staging: `intellia237-staging`

1. Open Firebase Console > App Check > Apps.
2. Register the Android app `com.intellia237.app.staging`.
3. Run a staging build and capture the SDK-generated debug token from the local
   device/emulator logs.
4. In the staging app's **Manage debug tokens** page, register that token with a
   tester/device label. Never paste it into Git, CI, chat, or Dart defines.
5. Exercise Auth, Firestore, Storage and every callable from approved staging
   devices.
6. Observe App Check request metrics for at least one complete staging release
   window. Investigate all `MISSING` and `INVALID` requests.

### Production: `edunova-aabd1`

1. Open Firebase Console > App Check > Apps.
2. Register `com.edunova.app` with the Play Integrity provider.
3. Confirm the production app is linked to the correct Google Play application
   and that signing certificates/package identity match the distributed app.
4. If required for supported devices, enable the Play Integrity setting that
   accepts basic device integrity in Google Play Console.
5. Release the App Check-enabled APK/AAB through an internal testing track.
6. Monitor valid/missing/invalid traffic for at least one release window before
   enabling enforcement.

Do not register a production debug token unless a controlled production-debug
test is explicitly approved. Delete any debug token immediately after that
test.

## Progressive enforcement

1. Ship client attestation with enforcement disabled.
2. Build a log-based metric from callable request verification logs and split
   it by `VALID`, `INVALID` and `MISSING`.
3. Resolve unsupported versions, tester tokens and platform gaps.
4. In a future reviewed code change, set `enforceAppCheck: true` on the three AI
   callables first and deploy only to staging.
5. Observe errors and attestation coverage, then extend to sensitive callables.
6. Enable Firestore and Storage enforcement from Firebase Console only after
   client coverage is complete.
7. Repeat the same sequence in production with a rollback owner and monitoring
   window assigned.

Do not enable `consumeAppCheckToken` during the first rollout. Replay protection
adds latency and attestation-provider quota usage and requires limited-use
tokens in client calls. Evaluate it later for low-volume, high-impact operations
such as payment review or AI generation.

## Rollback of enforcement

If legitimate clients are rejected after enforcement:

1. disable enforcement for the affected product/callable configuration;
2. confirm recovery using a known valid production build;
3. retain client-side App Check initialization so monitoring continues;
4. inspect verification metrics before attempting enforcement again.

Disabling enforcement does not require removing the client SDK or debug-token
registrations. Never work around an outage by committing a debug token.
